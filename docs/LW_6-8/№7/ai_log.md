GPT-6.

Спроектируй REST API-контракт для заявок.

Обязательно опиши:

1. HTTP-методы и URL.

### 7. Контекст, предоставленный модели

Были указаны используемые технологии, многоуровневая архитектура приложения, роли пользователей и основные поля сущности «Заявка».

| Метод | Endpoint | Назначение |

| GET | `/api/requests/` | Получение списка заявок |

| POST | `/api/requests/` | Создание заявки |
| PATCH | `/api/requests/{request_id}` | Редактирование заявки |
| PATCH | `/api/requests/{request_id}/executor` | Назначение исполнителя |
| PATCH | `/api/requests/{request_id}/status` | Изменение статуса заявки |

- идентификатор категории — положительное целое число;
- неизвестные дополнительные поля должны отклоняться;
- пробелы в начале и конце строк должны удаляться.

Также модель рекомендовала использовать HTTP-коды 200, 201, 400, 401, 403, 404 и 422 в зависимости от результата операции.

Для получения списка заявок были предложены параметры фильтрации по статусу, категории и тексту поиска.

Модель рекомендовала разграничивать доступ к заявкам в зависимости от роли пользователя и сохранять бизнес-логику в сервисном слое.

Предложенный контракт рассматривался как рекомендация и сопоставлялся с уже существующими маршрутами приложения. В результате были сохранены подходящие существующие операции и реализованы недостающие элементы API.

Предложенный контракт был сопоставлен с существующей архитектурой и реализованными API-методами проекта.

## Взаимодействие № 2. Критическая проверка API-контракта

### 1. Дата и этап

07.11.2026. Критический анализ спроектированного REST API, проверка валидации, HTTP-кодов, обработки ошибок, безопасности и удобства использования API.

### 2. Задача

Получить независимую оценку предложенного API-контракта, выявить возможные недостатки и определить, насколько он соответствует требованиям лабораторной работы и потребностям клиентского приложения.

### 3. Модель

GPT-6.

### 4. Промпт

«Ты выступаешь в роли независимого технического эксперта по REST API.

Проведи критическую проверку следующего API-контракта для системы обработки заявок.

Проверь контракт по следующим направлениям:

1. Полнота и согласованность endpoint'ов.
2. Корректность HTTP-методов и кодов ответов.
3. Валидация входных данных, включая пустые строки, длину полей, типы и идентификаторы.
4. Единообразие обработки ошибок.
5. Разграничение доступа и безопасность.
6. Защита персональных данных и паролей.
7. Удобство использования API frontend-клиентом.
8. Корректность фильтрации и поиска.

Для каждого найденного недостатка:

- объясни, в чём проблема;
- оцени её важность;
- предложи конкретное исправление.

Не ограничивайся общими рекомендациями. В конце выдели не менее трёх наиболее важных замечаний».

### 5. Контекст, предоставленный модели

Модели был предоставлен API-контракт, полученный в результате первого взаимодействия.

Дополнительно учитывались технологии проекта, архитектура приложения, роли пользователей, требования лабораторной работы и реализуемые операции над заявками.

### 6. Результат

При критической проверке были выделены следующие направления, требующие особого внимания.

**1. Валидация входных данных**

Необходимо проверять обязательность полей, длину строк, типы значений и допустимость идентификаторов. Следует отклонять пустые строки и неизвестные поля.

**2. Корректность HTTP-кодов**

Необходимо различать:

- 400 — ошибки бизнес-логики;
- 401 — отсутствие действительной авторизации;
- 403 — недостаточно прав;
- 404 — отсутствующий ресурс;
- 422 — ошибка валидации входных данных FastAPI/Pydantic.

**3. Разграничение доступа**

Проверка прав должна выполняться на сервере, а не только в интерфейсе. Пользователь не должен получать доступ к заявкам, которые ему недоступны по его роли.

**4. Защита данных пользователей**

API не должен возвращать хеши паролей и другие внутренние данные, которые не нужны клиентскому приложению.

**5. Фильтрация и поиск**

Параметры фильтрации должны иметь ограничения на допустимые значения. Поиск должен выполняться безопасными параметризованными SQL-запросами.

**6. Удобство клиентского приложения**

Ответы API должны иметь предсказуемую структуру, а ошибки должны содержать понятную информацию о причине отказа.

Отдельно было отмечено, что использование HTTP-метода PATCH предполагает частичное изменение ресурса. Если при обновлении обязательны все поля, это необходимо учитывать при выборе метода и описании контракта.

### 7. Самостоятельная проверка рекомендаций

Рекомендации были сопоставлены с реализованным кодом и результатами тестирования API.

**Проверка 1. Валидация входных данных**

Проверены ограничения для темы и описания заявки, обязательность полей, положительное значение идентификатора категории и запрет неизвестных дополнительных полей.

Также проверялись пустые строки и превышение допустимой длины описания.

Результат: сервер отклоняет некорректные данные с HTTP 422.

**Проверка 2. Фильтрация заявок**

Проверены запросы:

- получение списка заявок;
- фильтрация по статусу;
- фильтрация по категории;
- поиск по тексту;
- одновременное применение нескольких фильтров.

Результаты тестирования:

- `status_id=1` — получено 5 заявок;
- `category_id=1` — получено 4 заявки;
- `search=Тестовая заявка` — найдена 1 заявка;
- `status_id=1&category_id=1` — получено 3 заявки.

Результат: фильтрация и поиск работают, запросы возвращают HTTP 200.

**Проверка 3. Проверка граничных значений фильтров**

Выполнены запросы с недопустимым идентификатором статуса и слишком длинной поисковой строкой.

Результат: сервер возвращает HTTP 422, некорректные параметры не принимаются.

**Проверка 4. Получение отсутствующей заявки**

Выполнен запрос GET `/api/requests/99999`.

Результат: сервер возвращает HTTP 404.

**Проверка 5. Проверка разграничения доступа**

Проверены операции создания заявки и получения списка пользователей с учётом ролей.

Создание заявки пользователем с ролью администратора было отклонено с HTTP 403, поскольку операция доступна заявителю.

При получении списка пользователей администратор получает HTTP 200, а заявитель без необходимых прав получает HTTP 403.

Результат: проверка разграничения доступа пройдена.

**Проверка 6. Проверка ответа API пользователей**

Выполнен запрос GET `/api/users/` с правами администратора.

Результат: сервер возвращает список пользователей без поля `password_hash`.

**Проверка 7. Проверка операций изменения и удаления**

Проверены редактирование и удаление существующей заявки, а также обращение к отсутствующей заявке.

Результат:

- успешное редактирование — HTTP 200;
- успешное удаление — HTTP 200;
- обращение к отсутствующей заявке — HTTP 404.

**Проверка 8. Проверка документации и клиентского взаимодействия**

Проверены Swagger UI и сохранённая коллекция Postman, содержащая десять запросов к API.

Результат: документация API доступна, запросы сохранены в коллекции и используются для проверки работы endpoint'ов.

### 8. Принятые и отклонённые рекомендации

**Приняты:**

- проверка обязательности и длины входных строк;
- ограничение допустимых значений идентификаторов;
- запрет неизвестных полей в схемах создания и изменения заявки;
- разграничение доступа на серверной стороне;
- использование HTTP 401 и 403 для разных случаев отказа в доступе;
- использование HTTP 404 для отсутствующих ресурсов;
- применение фильтров и поиска с ограничениями входных параметров;
- использование параметризованных SQL-запросов;
- исключение хешей паролей из ответов API;
- сохранение коллекции Postman для повторного тестирования.

**Требуют отдельного внимания:**

**1. Использование PATCH для обновления заявки**

Схема `RequestUpdate` требует передачи всех трёх полей: `subject`, `description` и `category_id`. Поэтому фактически текущая операция PATCH принимает полный набор редактируемых полей, а не произвольное частичное обновление.

Замечание не было реализовано в виде изменения HTTP-метода, поскольку переход на PUT потребовал бы изменения существующего API-контракта и клиентских запросов. Текущая реализация сохранена осознанно, поскольку она уже используется приложением и проверена клиентскими запросами.

Возможность перехода на PUT либо реализации полноценного частичного обновления может рассматриваться отдельно.

**2. Единообразие формата ошибок**

Ошибки валидации FastAPI и ошибки бизнес-логики имеют разную структуру. Поэтому единый формат ошибок нельзя считать полностью унифицированным.

В рамках лабораторной работы сохранена существующая обработка ошибок. В дальнейшем возможно введение общего формата ответов об ошибках для повышения удобства frontend-клиента.

Переписывание существующей архитектуры для устранения этих замечаний не потребовалось.

### 9. Обоснование использования модели

Модель использовалась для независимой оценки API-контракта и формирования перечня проверок.

Рекомендации не принимались автоматически. Они сопоставлялись с существующими контроллерами, сервисами, схемами Pydantic и результатами запросов к тестовому API.

В результате были подтверждены реализованные механизмы валидации, фильтрации, разграничения доступа и обработки отсутствующих ресурсов. Отдельные замечания были зафиксированы как направления дальнейшего улучшения.

### 10. Итог и полученные знания

В результате взаимодействия были получены рекомендации по проектированию и критической оценке REST API.

Практическая проверка позволила убедиться в работоспособности основных endpoint'ов, корректности фильтрации, валидации и разграничения доступа.

Работа показала, что предложенный ИИ API-контракт необходимо сопоставлять с реальной архитектурой проекта и проверять практическими запросами. Не все рекомендации следует внедрять без учёта уже существующей реализации.
