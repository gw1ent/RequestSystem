# Журнал использования искусственного интеллекта

**Проект:** Система учёта заявок  
**Лабораторная работа:** № 6  
**Модель:** GPT-6  
**Дата работы:** 06.11.2026

## Взаимодействие № 1. Проектирование функции создания заявки

### 1. Дата и этап

06.11.2026. Анализ требований и проектирование функции создания заявки.

### 2. Задача

Получить рекомендации по проектированию создания заявки с учётом архитектуры приложения, проверки входных данных, бизнес-правил и сохранения информации в SQLite.

### 3. Модель

GPT-6.

### 4. Первоначальный слабый промпт

«Напиши функцию создания заявки для системы учёта заявок на Python. Она должна принимать данные от пользователя и сохранять заявку в базу данных».

### 5. Недостатки первоначального промпта

1. Не указана архитектура проекта и распределение ответственности между слоями.
2. Не описана структура базы данных и обязательные поля заявки.
3. Не определены правила валидации и проверки категории.
4. Не указано, откуда должен браться идентификатор заявителя.
5. Не определены требования к обработке ошибок и безопасности SQL-запросов.
6. Не задан формат результата, поэтому ответ мог содержать неподходящий или слишком общий код.

### 6. Улучшенный промпт

«Выступи в роли опытного Python backend-разработчика. Проанализируй проект системы учёта заявок на Python с использованием SQLite.

Контекст:
- Используется многоуровневая архитектура: Controllers, Services, Repositories.
- Основные таблицы: Users, Requests, Statuses, Categories.
- Таблица Requests содержит поля id, subject, description, applicant_id, executor_id, status_id, category_id, created_at.

Требуется спроектировать операцию создания заявки.

Условия:
1. Принимать заголовок, описание и идентификатор категории.
2. Проверять обязательность и корректность входных данных.
3. Проверять существование категории.
4. Получать заявителя из авторизованной сессии, а не доверять applicant_id от клиента.
5. Устанавливать начальный статус "Новая".
6. Сохранять заявку через Repository.
7. Использовать параметризованные SQL-запросы.
8. Предусмотреть обработку ошибок валидации, отсутствующей категории и ошибок базы данных.
9. Не размещать бизнес-логику в HTML или JavaScript.

Не изменяй файлы проекта и не создавай полный код. Представь последовательность действий, ответственность каждого слоя, сигнатуры методов, проверки, возможные ошибки и варианты тестирования. Отдельно укажи неоднозначности требований».

### 7. Контекст, предоставленный модели

Были указаны используемые технологии, архитектура приложения, основные таблицы базы данных и требования к созданию заявки.

### 8. Результат

Модель предложила разделить операцию создания заявки между контроллером, сервисом и репозиторием.

Основные рекомендации:
- контроллер принимает запрос и получает авторизованного пользователя;
- сервис проверяет бизнес-правила и корректность данных;
- репозиторий выполняет параметризованный SQL-запрос;
- заявитель определяется по авторизованной сессии;
- начальный статус устанавливается автоматически;
- ошибки обработки данных и базы данных должны быть понятными.

### 9. Проверка результата и принятые решения

Рекомендации сопоставлены с реализованной архитектурой проекта.

В проекте используются отдельные контроллеры, сервисы и репозитории. Создание заявки проверялось через пользовательский интерфейс и API. После создания данные были проверены непосредственно в SQLite.

Рекомендации по разделению ответственности, проверке категории, получению заявителя из сессии и параметризованным SQL-запросам соответствуют реализации и были приняты.

Полный сгенерированный код без проверки не использовался.

### 10. Сравнение промптов и вывод

Первоначальный промпт был слишком общим и не содержал достаточного контекста. Улучшенный промпт описывал архитектуру, структуру базы данных, бизнес-правила, ограничения безопасности и ожидаемый формат ответа.

В результате улучшенный промпт позволил получить более конкретные и применимые к проекту рекомендации.

## Взаимодействие № 2. Критический технический анализ системы

### 1. Дата и этап

06.11.2026. Проверка архитектуры, бизнес-правил, разграничения доступа и безопасности реализованного приложения.

### 2. Задача

Получить независимый критический анализ системы учёта заявок, определить потенциальные проблемы и составить перечень дополнительных проверок.

### 3. Модель

GPT-6.

### 4. Промпт

«Проведи критический технический разбор реализованной системы учёта заявок на Python.

Контекст проекта:
- Python 3.13, FastAPI, SQLite.
- Архитектура: Presentation → Controllers → Services → Repositories → Database.
- Пользовательский интерфейс взаимодействует с сервером через REST API.
- Авторизация реализована через сессии.
- Пароли хешируются с помощью Argon2.
- Существуют роли: Заявитель, Исполнитель, Оператор и Администратор.
- Реализованы создание, просмотр, редактирование, поиск, фильтрация, назначение исполнителя, изменение статуса и удаление заявок.
- Данные сохраняются в SQLite.
- Для проверки используется отдельная тестовая база данных.

Проверь разделение ответственности, валидацию, права доступа, обработку ошибок, безопасность паролей, сессий и SQL-запросов, а также необходимость дополнительных тестов.

Для каждого замечания укажи проблему, риск, серьёзность и рекомендуемое исправление.

Не предлагай переписывать проект целиком. Раздели замечания на критические, важные и дополнительные. Не утверждай, что проверил исходный код, если он не был предоставлен: явно отделяй подтверждённые сведения от предположений.

В конце составь список рекомендаций для лабораторной № 6 и отдельно укажи, что разумно оставить для следующих лабораторных работ».

### 5. Контекст, предоставленный модели

Были указаны архитектура приложения, технологии, роли пользователей, основные функции и использование отдельной тестовой базы данных.

### 6. Результат

Модель подтвердила, что многоуровневая архитектура соответствует назначению проекта.

Были выделены направления дополнительной проверки:
- защита бизнес-правил на уровне сервисов;
- проверка назначения исполнителей;
- разграничение доступа к заявкам;
- единый формат ошибок API;
- защита сессий от CSRF;
- исключение хешей паролей из ответов API;
- проверка параметризованных SQL-запросов;
- контроль пути к базе данных;
- проверка транзакций.

Модель отдельно отметила, что часть замечаний является потенциальной и требует практической проверки.

### 7. Самостоятельная проверка рекомендаций

Были проведены три дополнительные проверки на тестовой базе данных.

**Проверка 1. Отсутствие хешей паролей в API**

Выполнен запрос GET /api/users/ с правами администратора.

Получен ответ HTTP 200 со списком шести пользователей. Поле password_hash в ответе отсутствовало.

Результат: проверка пройдена.

**Проверка 2. Запрет назначения пользователя неподходящей роли**

Выполнена попытка назначить пользователя с ID 2, имеющего роль «Оператор», исполнителем заявки.

Сервер вернул ошибку:

```json
{
  "detail": "Пользователь не является исполнителем"
}
```

Результат: проверка пройдена. Сервер отклонил назначение пользователя с неподходящей ролью.

**Проверка 3. Проверка поиска на SQL-инъекции**

В поле поиска последовательно введены строки:

```text
' OR 1=1 --
'; DROP TABLE Requests; --
```

В обоих случаях результатов не было. Ошибок SQL не возникло.

После этого обычный поиск по слову Outlook продолжил работать.

Результат: проверенные поисковые строки не привели к выполнению SQL-команд или нарушению работы базы данных. Обычный поиск продолжил работать. Проверка не является полным аудитом защиты от SQL-инъекций.

### 8. Принятые и отклонённые рекомендации

Приняты:
- провести дополнительные проверки безопасности;
- убедиться, что API не возвращает хеши паролей;
- проверить назначение исполнителя с неподходящей ролью;
- проверить обработку поисковых строк;
- сохранить результаты проверок в отчёте.

Оставлены для дальнейшей работы:
- CSRF-токены или дополнительная проверка Origin;
- расширение автоматизированных тестов;
- улучшение контроля конфигурации базы данных;
- единый формат ошибок API;
- дополнительные проверки транзакций и граничных значений.

Переписывание архитектуры не потребовалось.

### 9. Обоснование использования модели

Модель использовалась для независимого анализа архитектуры и формирования перечня проверок. Результаты не принимались автоматически: рекомендации проверялись через реальные API-запросы и пользовательский интерфейс.

### 10. Итог и полученные знания

В результате взаимодействия были выявлены направления дополнительной проверки безопасности. Три выбранные проверки завершились успешно.

Работа показала, что ответы ИИ необходимо проверять самостоятельно, поскольку рекомендации могут быть общими или относиться к потенциальным, а не подтверждённым проблемам проекта.
