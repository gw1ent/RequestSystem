## 1. Запрос модели на разработку Dockerfile для проекта

На первом этапе искусственный интеллект использовался для подготовки Dockerfile с учётом архитектуры и особенностей существующего приложения.

Для этого модели был передан следующий промпт.

**Промпт № 1 — разработка Dockerfile:**

```text
Я разрабатываю веб-приложение «Система учёта заявок» и выполняю лабораторную работу по контейнеризации и развёртыванию приложения.

Помоги подготовить Dockerfile для моего проекта.

Характеристики проекта:
- Язык программирования: Python 3.13.
- Веб-фреймворк: FastAPI.
- База данных: SQLite.
- Файл зависимостей: requirements.txt.
- Исходный код приложения находится в каталоге src/.
- SQL-файлы и скрипт инициализации базы данных находятся в каталоге db/.
- Точка входа приложения: src.main:app.
- Команда запуска веб-сервера: python -m uvicorn src.main:app.
- Порт приложения: 8000.
- Скрипт db/run_queries.py выполняет подготовку базы данных и добавление начальных данных.

Требования к Dockerfile:
1. Использовать официальный образ Python 3.13.
2. По возможности выбрать облегчённый базовый образ.
3. Устанавливать зависимости из requirements.txt.
4. Организовать слои Docker так, чтобы установка зависимостей кешировалась отдельно от исходного кода.
5. Запускать приложение от непривилегированного пользователя.
6. Предусмотреть каталог /data для хранения SQLite и возможность подключения Docker volume.
7. Путь к базе данных должен задаваться через переменную окружения DATABASE_PATH.
8. Секретный ключ сессии SESSION_SECRET_KEY не должен быть записан непосредственно в Dockerfile.
9. Предусмотреть передачу настроек через переменные окружения.
10. Добавить HEALTHCHECK для проверки работоспособности приложения.
11. Перед запуском Uvicorn необходимо выполнить python db/run_queries.py.

Сначала предложи Dockerfile, затем кратко объясни назначение его основных инструкций. Не изменяй архитектуру приложения и не предлагай замену SQLite или FastAPI.
```

По результатам запроса модель предложила использовать официальный облегчённый образ Python, устанавливать зависимости отдельным слоем, копировать исходный код, создавать непривилегированного пользователя и запускать приложение через Uvicorn.

Также было предусмотрено выполнение скрипта инициализации базы данных перед запуском веб-сервера.

Полученное предложение использовалось как основа для подготовки Dockerfile, но не принималось без самостоятельной проверки.

## 2. Ревью подготовленного Dockerfile

После подготовки Dockerfile модель использовалась в качестве технического ревьюера инфраструктуры.

**Промпт № 2 — техническое ревью Dockerfile:**

```text
Проведи техническое ревью Dockerfile моего проекта «Система учёта заявок».

Технологии проекта:
- Python 3.13.
- FastAPI.
- SQLite.
- Uvicorn.
- Зависимости устанавливаются из requirements.txt.
- Исходный код находится в src/.
- SQL-файлы и скрипт инициализации базы данных находятся в db/.
- Точка входа: src.main:app.
- Порт приложения: 8000.
- База данных должна храниться в /data и подключаться через Docker volume.

Проверь Dockerfile по следующим критериям:

1. Безопасность:
   - от какого пользователя запускается приложение;
   - есть ли необходимость использовать отдельного непривилегированного пользователя;
   - не запускается ли приложение с избыточными правами.

2. Размер образа:
   - насколько оправдан выбранный базовый образ;
   - можно ли уменьшить размер итогового образа без ущерба работоспособности.

3. Кеширование:
   - правильно ли организовано копирование requirements.txt;
   - можно ли избежать повторной установки зависимостей при изменении исходного кода.

4. Порты:
   - корректно ли объявлен порт приложения;
   - соответствует ли он команде запуска Uvicorn.

5. Права доступа:
   - сможет ли приложение создавать и изменять файл SQLite;
   - корректно ли настроены права на каталог /data.

6. Секреты:
   - отсутствуют ли реальные секретные значения в Dockerfile;
   - передаётся ли SESSION_SECRET_KEY через переменную окружения.

7. Health-check:
   - предусмотрена ли проверка работоспособности контейнера;
   - корректно ли она выполняется.

Не переписывай весь проект и не предлагай необоснованную смену технологий.
Для каждого найденного недостатка:
- объясни, почему это проблема;
- предложи конкретное исправление;
- укажи, насколько оно важно.

В конце выдели наиболее полезные улучшения, которые можно применить без изменения архитектуры приложения.
```

По результатам ревью были рассмотрены следующие решения:

- Использование `python:3.13-slim` вместо более тяжёлого базового образа.
- Копирование `requirements.txt` до копирования исходного кода.
- Установка зависимостей отдельным слоем.
- Использование `pip install --no-cache-dir`.
- Создание отдельного пользователя `app`.
- Предоставление пользователю `app` прав на каталог `/data`.
- Передача `SESSION_SECRET_KEY` через переменную окружения.
- Добавление Docker HEALTHCHECK.

## 3. Самостоятельная проверка замечаний модели

После получения рекомендаций требовалось определить, насколько они подходят для фактической структуры проекта.

**Промпт № 3 — проверка применимости рекомендаций:**

```text
Проанализируй рекомендации, полученные при ревью Dockerfile моего приложения.

Необходимо оценить их применимость с учётом следующих особенностей проекта:

- Python 3.13 и FastAPI.
- SQLite используется как основная база данных.
- Инициализация базы данных выполняется скриптом db/run_queries.py.
- Файл базы данных должен находиться в /data/RequestSystem.db.
- Каталог /data подключается к Docker volume.
- Приложение запускается через Uvicorn.
- Конфигурация приложения использует переменные окружения DATABASE_PATH,
  SESSION_SECRET_KEY и SESSION_HTTPS_ONLY.

Проверь следующие рекомендации:
1. Использование python:3.13-slim.
2. Раздельное кеширование зависимостей и исходного кода.
3. Установка зависимостей через pip install --no-cache-dir.
4. Запуск от отдельного пользователя app.
5. Изменение владельца каталога /data.
6. Передача секретного ключа через переменную окружения.
7. Использование HEALTHCHECK.

Для каждой рекомендации укажи:
- подходит ли она моему проекту;
- почему она полезна или не нужна;
- какие условия необходимо выполнить для её корректной работы;
- как проверить результат после применения.

Не предлагай изменения, которые нарушают работу SQLite, инициализацию базы данных или запуск FastAPI.
Отделяй подтверждённые технические требования от предположений.
```

Рекомендации модели были сопоставлены с фактической структурой проекта и проверены при локальной сборке и запуске контейнера.

**Базовый образ и зависимости**

Для проекта подходит `python:3.13-slim`, поскольку приложение использует Python 3.13, а облегчённый вариант образа позволяет не включать в контейнер лишние компоненты.

Зависимости устанавливаются из `requirements.txt`. Этот файл копируется отдельно от исходного кода, поэтому Docker может повторно использовать слой с установленными библиотеками при изменении файлов приложения.

**Права доступа**

В Dockerfile создаётся системная группа и пользователь `app`. Исходный код копируется с соответствующими правами, а каталог `/data` перед запуском приложения передаётся во владение пользователю `app`.

Это позволяет запускать приложение без использования учётной записи root и обеспечивает возможность работы с файлом SQLite.

**Секреты и переменные окружения**

Секретный ключ `SESSION_SECRET_KEY` не задаётся непосредственно в Dockerfile. Он передаётся контейнеру при запуске через переменную окружения.

Путь к базе данных задаётся через `DATABASE_PATH`, а режим защищённых cookie — через `SESSION_HTTPS_ONLY`.

Для демонстрации конфигурации используется `.env.example`, в котором отсутствуют реальные секретные значения.

**Проверка работоспособности**

В Dockerfile добавлен HEALTHCHECK, который выполняет HTTP-запрос к `/docs` внутри контейнера.

После сборки и запуска контейнера проверялся его статус. Контейнер перешёл в состояние `healthy`, что подтвердило успешное прохождение настроенной проверки доступности приложения.

Дополнительно была проверена доступность отдельного endpoint `/health`, возвращающего ответ `{"status":"healthy"}`.

Таким образом, рекомендации модели не принимались автоматически: их применимость оценивалась с учётом особенностей FastAPI, SQLite, структуры проекта и фактического поведения контейнера.

## 4. Исправление замечания и сравнение результата до и после

В качестве инфраструктурного улучшения был реализован запуск приложения от отдельного непривилегированного пользователя.

**До исправления:** при отсутствии явного указания пользователя Docker запускает процесс контейнера от root. Такой подход предоставляет приложению избыточные права внутри контейнера.

**После исправления:** в Dockerfile создаются отдельная системная группа и пользователь `app`, исходные файлы копируются с соответствующими правами, каталог `/data` передаётся во владение этому пользователю, а запуск выполняется после инструкции `USER app`.

В результате приложение работает с ограниченными правами, но сохраняет возможность обращаться к базе данных SQLite в подключённом томе.

После подготовки Dockerfile была выполнена сборка образа и запуск контейнера. Контейнер успешно запустился, получил статус `healthy`, а веб-приложение стало доступно через локальный адрес.

Эти ограничения позволили сосредоточить анализ на реальных задачах контейнеризации существующего приложения и избежать рекомендаций, которые потребовали бы необоснованного изменения его архитектуры.
