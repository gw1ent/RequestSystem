# Система учёта заявок

Веб-приложение для регистрации, обработки и контроля заявок пользователей.

## Возможности

- Авторизация пользователей и управление сессиями.
- Создание и просмотр заявок.
- Редактирование и удаление заявок в соответствии с правами доступа.
- Назначение исполнителей.
- Изменение статусов заявок.
- Управление пользователями и категориями.
- Поиск и фильтрация заявок.
- REST API для взаимодействия с серверной частью.
- Документация API на Swagger UI.

## Технологии

- Python 3.13
- FastAPI
- SQLite
- Pydantic
- Argon2
- Uvicorn
- HTML, CSS, JavaScript

## Установка и запуск

### 1. Клонирование репозитория

```powershell
git clone https://github.com/gw1ent/RequestSystem.git
cd RequestSystem
```

Для получения актуальной версии лабораторной работы:

```powershell
git checkout develop
git pull origin develop
```

### 2. Создание виртуального окружения

```powershell
python -m venv .venv
```

Активация в Windows PowerShell:

```powershell
.\.venv\Scripts\Activate.ps1
```

### 3. Установка зависимостей

```powershell
python -m pip install --upgrade pip
pip install -r requirements.txt
```

### 4. Настройка переменных окружения

Для локального запуска необходимо задать секретный ключ сессии:

```powershell
$env:SESSION_SECRET_KEY = python -c "import secrets; print(secrets.token_urlsafe(32))"
```

Для работы с тестовой базой данных:

```powershell
$env:DATABASE_PATH = "db/RequestSystem_test.db"
$env:SESSION_HTTPS_ONLY = "false"
```

**Важно:** тестовая база данных используется для проверки приложения. Не указывайте путь к основной базе данных, если хотите сохранить её содержимое без изменений.

### 5. Подготовка базы данных

Перед первым запуском приложения из корневой папки проекта выполните:

```powershell
python db/run_queries.py
```

Скрипт подготовит структуру базы данных и добавит необходимые начальные данные. Путь к базе определяется переменной `DATABASE_PATH`.

При использовании тестовой базы данных будет создан или использован файл `db/RequestSystem_test.db`.

### 6. Запуск приложения

Из корневой папки проекта выполните:

```powershell
python -m uvicorn src.main:app --reload
```

После успешного запуска сервер будет доступен по адресу:

[http://127.0.0.1:8000/](http://127.0.0.1:8000/)

## REST API

REST API предоставляет возможность взаимодействия с системой учёта заявок посредством HTTP-запросов. Все основные маршруты API имеют префикс `/api`.

Интерактивная документация доступна по адресу `http://127.0.0.1:8000/docs`.

### Основные эндпоинты

| Метод | Эндпоинт | Описание | Основные ответы |
|---|---|---|---|
| GET | `/api/requests/` | Получение списка заявок | 200, 401, 422 |
| GET | `/api/requests/{request_id}` | Получение заявки по ID | 200, 401, 403, 404 |
| POST | `/api/requests/` | Создание заявки | 201, 400, 401, 403, 422 |
| PATCH | `/api/requests/{request_id}` | Редактирование заявки | 200, 400, 401, 403, 404, 422 |
| PATCH | `/api/requests/{request_id}/executor` | Назначение исполнителя | 200, 400, 401, 403, 404, 422 |
| PATCH | `/api/requests/{request_id}/status` | Завершение заявки исполнителем | 200, 400, 401, 403, 404 |
| PATCH | `/api/requests/{request_id}/close` | Закрытие заявки | 200, 400, 401, 403, 404 |
| DELETE | `/api/requests/{request_id}` | Удаление заявки | 200, 400, 401, 403, 404 |
| GET | `/api/users/` | Получение списка пользователей (только для администратора) | 200, 401, 403 |
| GET | `/api/statuses/` | Получение списка статусов | 200, 401 |
| GET | `/api/categories/` | Получение списка категорий | 200, 401 |
| GET | `/api/users/executors` | Получение списка активных исполнителей | 200, 401, 403 |

### Параметры фильтрации заявок

Для получения списка заявок (`GET /api/requests/`) предусмотрены следующие необязательные query-параметры:

| Параметр | Тип | Ограничения | Описание |
|---|---|---|---|
| `status_id` | integer | Больше 0 | Фильтрация по ID статуса |
| `category_id` | integer | Больше 0 | Фильтрация по ID категории |
| `search` | string | До 200 символов | Поиск по теме и описанию заявки |

Параметры можно использовать отдельно или совместно.

Примеры запросов:

```http
GET /api/requests/?status_id=1
GET /api/requests/?category_id=1
GET /api/requests/?search=Тестовая%20заявка
GET /api/requests/?status_id=1&category_id=1
```

### Пример создания заявки

Запрос:

```http
POST /api/requests/
Content-Type: application/json
```

Тело запроса:

```json
{
  "subject": "Проверка создания через API",
  "description": "Тестовая заявка для лабораторной работы",
  "category_id": 1
}
```

При успешном создании возвращается HTTP `201 Created` и JSON с данными созданной заявки.

### Обработка ошибок

API использует стандартные HTTP-коды для обозначения результата выполнения запросов:

- `200 OK` — запрос успешно выполнен.
- `201 Created` — ресурс успешно создан.
- `400 Bad Request` — ошибка бизнес-логики или некорректные данные.
- `401 Unauthorized` — отсутствует авторизация или сессия недействительна.
- `403 Forbidden` — недостаточно прав для выполнения операции.
- `404 Not Found` — запрашиваемый ресурс или связанный объект не найден.
- `422 Unprocessable Entity` — ошибка проверки входных данных.

Доступ к API ограничен авторизацией и ролевой моделью. Возможность выполнения операций зависит от роли пользователя.

## Архитектура приложения

Проект использует многоуровневую архитектуру:

1. **Presentation** — пользовательский интерфейс.
2. **Controllers** — обработка HTTP-запросов.

Такое разделение позволяет отделить пользовательский интерфейс, обработку запросов, бизнес-логику и операции с базой данных.

Структура базы данных и начальные данные находятся в каталоге `db/`.

# Контейнеризация приложения (Docker)

Для запуска приложения вне локального Python-окружения используется Docker. Приложение упаковывается в Docker-образ, содержащий необходимые зависимости и файлы проекта.

SQLite хранится в отдельном Docker volume, поэтому данные не удаляются при пересоздании контейнера.

### 1. Требования для запуска через Docker

Перед началом работы необходимо установить:

- Docker Desktop;
- WSL 2 для Windows (если используется Linux-контейнеризация);
- Git для получения исходного кода проекта;
- Python 3.13 или совместимую версию — для генерации секретного ключа сессии при запуске контейнера из PowerShell.

Проверить установку Docker можно командами:

```powershell
docker --version
docker compose version
```

Убедитесь, что Docker Desktop запущен и использует Linux-контейнеры.

### 2. Конфигурация окружения

В корне проекта находится файл `.env.example`. Он содержит пример переменных окружения, необходимых приложению:

```dotenv
PORT=8000
DATABASE_PATH=/data/RequestSystem.db
SESSION_SECRET_KEY=replace-with-a-random-secret
SESSION_HTTPS_ONLY=true
```

Файл `.env.example` не содержит действительных секретов и предназначен для ознакомления с настройками приложения.

Секретный ключ сессии необходимо генерировать отдельно для каждого окружения. Не следует хранить настоящие секретные ключи в Git или публиковать их.

Для локального запуска контейнера переменные окружения передаются непосредственно при выполнении `docker run`. Создавать файл `.env` для приведённой ниже команды не требуется.

### 3. Сборка Docker-образа

Из корневой папки проекта выполните:

```powershell
docker build -t requestsystem:lab8 .
```

Команда создаёт Docker-образ с именем `requestsystem` и тегом `lab8`.

Проверить наличие собранного образа можно командой:

```powershell
docker images requestsystem
```

### 4. Создание хранилища базы данных

Для сохранения данных SQLite используется именованный Docker volume:

```powershell
docker volume create requestsystem-data
```

Проверить наличие тома:

```powershell
docker volume ls
```

Том `requestsystem-data` хранит базу данных отдельно от файлов контейнера.

### 5. Запуск контейнера

Для локального запуска контейнера в Windows PowerShell выполните:

```powershell
$sessionSecret = python -c "import secrets; print(secrets.token_urlsafe(32))"

docker run -d `
  --name requestsystem-app `
  --restart unless-stopped `
  -p 8000:8000 `
  -e SESSION_SECRET_KEY="$sessionSecret" `
  -e SESSION_HTTPS_ONLY=false `
  -v requestsystem-data:/data `
  requestsystem:lab8
```

Команды следует выполнять в одном окне PowerShell, чтобы переменная `$sessionSecret` оставалась доступной при запуске контейнера.

Ожидаемый результат — Docker выведет идентификатор созданного контейнера.

Назначение параметров:

- `-d` — запуск контейнера в фоновом режиме.
- `--name` — имя контейнера.
- `--restart unless-stopped` — автоматический перезапуск контейнера, если он завершился или Docker перезапустился.
- `-p 8000:8000` — публикация порта приложения на локальной машине.
- `-e SESSION_SECRET_KEY` — передача секретного ключа сессии.
- `-e SESSION_HTTPS_ONLY=false` — отключение требования HTTPS для локальной проверки по HTTP.
- `-v requestsystem-data:/data` — подключение постоянного хранилища базы данных.
- `requestsystem:lab8` — используемый Docker-образ.

При каждом запуске контейнера выполняется проверка и подготовка схемы базы данных, а также добавление недостающих начальных данных с помощью `db/run_queries.py`. После этого запускается FastAPI через Uvicorn.

### 6. Проверка состояния контейнера

Проверить запущенные контейнеры:

```powershell

```

Посмотреть все контейнеры, включая остановленные:

```powershell

```

В столбце `STATUS` для успешно запущенного приложения ожидается состояние `Up ... (healthy)`.

Проверка работоспособности контейнера выполняется средствами Docker. Контейнер проверяет доступность документации API по адресу `/docs`.

### 10. Обновление Docker-образа

После изменения исходного кода приложения необходимо пересобрать образ:

```powershell
docker build -t requestsystem:lab8 .
```

Если контейнер с таким именем уже существует, его необходимо остановить и удалить:

```powershell
docker stop requestsystem-app
docker rm requestsystem-app
```

После этого контейнер можно создать заново командой запуска из раздела 5.

**Важно:** удаление контейнера не удаляет именованный Docker volume `requestsystem-data`. При повторном запуске с тем же томом приложение использует сохранённую базу данных.

Не удаляйте том командой `docker volume rm`, если необходимо сохранить данные.

### 11. Хранение данных

Файл SQLite внутри контейнера располагается по пути:

```text
/data/RequestSystem.db
```

Каталог `/data` подключается к именованному Docker volume `requestsystem-data`.

Такое разделение позволяет:

- сохранять данные при остановке контейнера;
- сохранять данные при удалении и повторном создании контейнера;
- отделять файлы приложения от пользовательских данных.

При переносе приложения на другой сервер необходимо отдельно обеспечить перенос или резервное копирование содержимого Docker volume.

### 12. Безопасность

- Настоящий `SESSION_SECRET_KEY` не должен попадать в Git.
- Для локального тестирования по HTTP используется `SESSION_HTTPS_ONLY=false`.
- Для удалённого развёртывания с настроенным HTTPS необходимо использовать `SESSION_HTTPS_ONLY=true`.
- Не следует публиковать секретные ключи, пароли и содержимое файлов с реальными настройками.
- Доступ к удалённому серверу и его портам необходимо ограничивать правилами сетевой безопасности.

# Развёртывание в Yandex Cloud

Для удалённого размещения приложения использовалась облачная платформа Yandex Cloud, сервис Compute Cloud. Приложение развёрнуто на виртуальной машине с Ubuntu и запускается в Docker-контейнере.

## 1. Создание виртуальной машины

В консоли Yandex Cloud необходимо создать виртуальную машину со следующими параметрами:

| Параметр | Значение |
| --- | --- |
| Имя виртуальной машины | `requestsystem-vm-2` |
| Сервис | Yandex Compute Cloud |
| Операционная система | Ubuntu 24.04 LTS |
| Зона доступности | `ru-central1-d` |
| Количество vCPU | 2 |
| Объём оперативной памяти | 4 ГБ |
| Диск | SSD, 20 ГБ |
| Пользователь SSH | `requestsystem2` |

Для подключения к виртуальной машине используется SSH-ключ.

В настройках группы безопасности необходимо разрешить входящие подключения:

- TCP 22 — для SSH-подключения;
- TCP 8000 — для доступа к приложению.

Для реального публичного использования рекомендуется ограничить SSH-доступ доверенными IP-адресами. Также рекомендуется разрешать только те входящие подключения, которые необходимы для работы сервера.

После создания виртуальной машины необходимо сохранить её публичный IP-адрес.

В рамках данного развёртывания использован адрес:

`158.160.191.27`

## 2. Подключение к виртуальной машине

В Windows PowerShell выполните:

```powershell
ssh -i "$env:USERPROFILE\.ssh\id_ed25519" requestsystem2@158.160.191.27
```

При первом подключении необходимо подтвердить доверие к SSH-ключу сервера.

После успешного подключения команды выполняются в терминале удалённой виртуальной машины.

## 3. Установка Docker на сервер

Сначала обновите список пакетов:

```bash
sudo apt update
sudo apt upgrade -y
```

Установите пакеты, необходимые для подключения официального репозитория Docker:

```bash
sudo apt install -y ca-certificates curl
```

Создайте каталог для ключей репозиториев:

```bash
sudo install -m 0755 -d /etc/apt/keyrings
```

Добавьте официальный ключ Docker:

```bash
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
```

Добавьте репозиторий Docker:

```bash
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo "$VERSION_CODENAME") stable" | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null
```

Обновите список пакетов и установите Docker с необходимыми компонентами:

```bash
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
```

Проверьте установку:

```bash
sudo docker --version
sudo docker compose version
```

Дополнительно проверьте возможность запуска контейнеров:

```bash
sudo docker run --rm hello-world
```

При успешной установке Docker выведет сообщение о том, что установка и запуск контейнера прошли успешно.

## 4. Передача проекта на сервер

Для развёртывания необходимо подготовить архив проекта и передать его на виртуальную машину.

В архив не следует включать:

- каталог `.git`;
- виртуальное окружение `.venv`;
- каталог `.idea`;
- файл `.env`;
- локальные файлы базы данных SQLite.

Файл `.env.example` должен присутствовать в проекте, поскольку он содержит пример конфигурации без действительных секретов.

Для создания архива откройте Windows PowerShell в корневом каталоге проекта и выполните:

```powershell
tar -czf "$env:TEMP\RequestSystem-deploy.tar.gz" `
  --exclude=".git" `
  --exclude=".venv" `
  --exclude=".idea" `
  --exclude=".env" `
  --exclude="*.db" `
  --exclude="*.sqlite3" `
  .
```

Архив будет создан во временном каталоге Windows.

Передача архива выполняется из Windows PowerShell:

```powershell
scp -i "$env:USERPROFILE\.ssh\id_ed25519" "$env:TEMP\RequestSystem-deploy.tar.gz" requestsystem2@158.160.191.27:~/
```

На сервере создайте каталог проекта и распакуйте архив:

```bash
mkdir -p ~/RequestSystem
tar -xzf ~/RequestSystem-deploy.tar.gz -C ~/RequestSystem
cd ~/RequestSystem
```

Убедитесь, что в каталоге присутствуют `Dockerfile`, `.dockerignore`, `.env.example`, `requirements.txt`, а также каталоги `src/` и `db/`.

## 7. Настройка и запуск приложения

Для удалённого окружения необходимо создать отдельный секретный ключ сессии. Секрет генерируется непосредственно на сервере:

```bash
openssl rand -hex 32
```

Полученное значение необходимо сохранить в безопасном месте и использовать при запуске контейнера. Не следует публиковать его или добавлять в Git.

Запустите контейнер:

```bash
sudo docker run -d \
  --name requestsystem-app \
  --restart unless-stopped \
  -p 8000:8000 \
  -e SESSION_SECRET_KEY='ВАШ_СГЕНЕРИРОВАННЫЙ_СЕКРЕТ' \
  -e SESSION_HTTPS_ONLY=false \
  -v requestsystem-data:/data \
  requestsystem:cloud
```

Вместо `ВАШ_СГЕНЕРИРОВАННЫЙ_СЕКРЕТ` необходимо подставить сгенерированное значение.

Параметры запуска:

- `-d` — запуск контейнера в фоновом режиме;
- `--name` — имя контейнера;
- `--restart unless-stopped` — автоматический перезапуск контейнера;
- `-p 8000:8000` — публикация порта приложения;
- `-e SESSION_SECRET_KEY` — передача секретного ключа сессии;
- `-e SESSION_HTTPS_ONLY=false` — разрешение работы с сессиями по HTTP в рамках лабораторного развёртывания без HTTPS;
- `-v requestsystem-data:/data` — подключение постоянного хранилища SQLite;
- `requestsystem:cloud` — используемый Docker-образ.

При запуске контейнера выполняется подготовка базы данных с помощью `db/run_queries.py`, после чего запускается сервер Uvicorn.

# Автоматизированное тестирование (Lab 10)

Для проверки бизнес-логики, REST API и разграничения доступа в проекте используются автоматизированные тесты на Python с применением `pytest` и `FastAPI TestClient`.

## 1. Зависимости для тестирования

Основные зависимости приложения устанавливаются стандартной командой:

```powershell
pip install -r requirements.txt
```

Для запуска автоматизированных тестов дополнительно необходимы:

- `pytest` — запуск и организация тестов;
- `httpx` — HTTP-клиент, используемый FastAPI TestClient.

Установка дополнительных зависимостей:

```powershell
python -m pip install pytest==9.2.0 httpx==0.28.1
```

Проверить установку pytest можно командой:

```powershell
python -m pytest --version
```

## 2. Структура автоматизированных тестов

Тесты лабораторной работы № 10 находятся в каталоге `testing/lab10/`:

```text
testing/
└── lab10/
    ├── conftest.py
    ├── test_request_service.py
    ├── test_request_api.py
    ├── test_request_access.py
    ├── test_run.txt
    ├── test_summary.md
    └── ai_log.md
```

Назначение файлов:

- `conftest.py` — общие фикстуры, тестовый клиент и подготовка тестовой базы данных;
- `test_request_service.py` — проверка бизнес-логики работы с заявками;
- `test_request_api.py` — проверка API, успешных запросов и обработки некорректных данных;
- `test_request_access.py` — проверка разграничения доступа между пользователями и ролями;
- `test_run.txt` — сохранённый результат запуска автоматизированных тестов;
- `test_summary.md` — итоговый отчёт по тестированию;
- `ai_log.md` — журнал использования искусственного интеллекта.

## 3. Тестовая база данных

Автоматизированные тесты используют отдельную временную базу SQLite.

Для каждого теста создаётся собственный файл базы данных во временном каталоге. Структура и начальные данные загружаются из:

- `db/schema.sql`;
- `db/seed.sql`.

После завершения теста соединение с базой данных закрывается.

Такой подход позволяет изолировать тестовые данные и не затрагивать основную базу данных приложения.

**Важно:** для запуска автоматизированных тестов не требуется выполнять `db/run_queries.py` и изменять основную базу данных.

## 4. Запуск автоматизированных тестов

Все тесты лабораторной работы № 10 запускаются из корневой папки проекта одной командой:

```powershell
python -m pytest testing/lab10 -v
```

Параметр `-v` включает подробный вывод: отображаются имена тестов
