## 2. Цель тестирования

Целью работы являлись автоматизация проверки ключевых функций RequestSystem, проведение регрессионного тестирования и оценка готовности продукта к итоговой демонстрации.

В ходе работы использовались результаты ручного тестирования Lab 9, на основе которых были выбраны критические сценарии для автоматизации.

Для автоматизации применялся pytest. Проверки API выполнялись с помощью FastAPI TestClient. Для тестирования использовалась отдельная временная база данных SQLite, создаваемая для каждого теста. Рабочая база данных приложения не использовалась.

## 5. Автоматизированные тесты Lab 10

В рамках Lab 10 реализовано 10 автоматизированных тестов с использованием pytest.

### 5.1. Проверки бизнес-логики

Реализованы четыре теста:

1. `test_create_request_success` — успешное создание заявки.
2. `test_blocked_user_cannot_create_request` — запрет создания заявки заблокированным пользователем.
3. `test_assign_executor_success` — успешное назначение исполнителя.
4. `test_complete_assigned_request_success` — успешное завершение назначенной заявки.

Эти проверки обращаются непосредственно к сервисному слою приложения и проверяют результаты выполнения бизнес-операций.

### 5.2. Проверки API

Реализованы четыре теста:

1. `test_create_request_api_success` — успешное создание заявки через API.
2. `test_create_request_api_invalid_data` — отклонение запроса с пустой темой.
3. `test_create_request_api_invalid_category` — отклонение запроса с недопустимым идентификатором категории.
4. `test_get_nonexistent_request_api` — получение ответа 404 при запросе несуществующей заявки.

Проверки выполняются через FastAPI TestClient с анализом HTTP-статусов и содержимого ответов.

### 5.3. Проверки прав доступа и регрессии

Реализованы два теста:

1. `test_applicant_cannot_view_another_users_request` — заявитель не может просматривать заявку другого пользователя.
2. `test_executor_cannot_complete_another_executors_request` — исполнитель не может завершить заявку, назначенную другому исполнителю.

Эти тесты проверяют критически важные ограничения доступа и относятся к регрессионным проверкам рискованных требований системы.

## 7. Проверка способности автоматического теста обнаруживать ошибку

Для подтверждения того, что автоматизированный тест действительно способен обнаруживать нарушения, был проведён отдельный эксперимент на изолированной копии проекта.

В контроллере временно отключили проверку принадлежности заявки заявителю. После этого запустили тест:

`test_applicant_cannot_view_another_users_request`

В результате API вернул HTTP 200 OK, хотя тест ожидал HTTP 403 Forbidden.

Тест завершился с ошибкой:

`assert 200 == 403`

Таким образом, автоматизированная проверка обнаружила нарушение разграничения доступа.

После эксперимента исходная проверка была восстановлена в экспериментальной копии. Рабочий репозиторий и его исходный код не изменялись в ходе эксперимента.

Эксперимент подтвердил, что тест проверяет фактический результат работы API и способен выявлять нарушение критического требования безопасности.
