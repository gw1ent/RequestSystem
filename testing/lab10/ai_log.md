## Взаимодействие № 1. Подготовка автоматизированных тестов

### 1. Дата и этап

09.11.2026. Изучение структуры проекта и подготовка автоматизированных тестов для проверки бизнес-логики, REST API и разграничения доступа.

### 2. Задача

Использовать модель для подготовки автоматизированных тестов на Python с применением pytest и FastAPI TestClient.

Требовалось проверить наиболее важные операции системы:
- создание заявки;
- назначение исполнителя;
- завершение заявки;
- обработку некорректных входных данных;
- обработку обращения к несуществующей заявке;
- соблюдение ограничений доступа для разных ролей пользователей.

Дополнительное требование — тесты должны работать с отдельной тестовой базой данных и не затрагивать реальные данные приложения.

### 3. Модель

GPT-6.

### 4. Промпт

```text
Ты выступаешь в роли QA Automation Engineer.

Необходимо подготовить автоматизированные тесты для существующего
проекта «Система учёта заявок».

Технологии проекта:
- Python 3.13;
- FastAPI;
- SQLite;
- Pydantic;
- pytest;
- FastAPI TestClient.

Архитектура проекта разделена на контроллеры, сервисы,
репозитории и слой базы данных.

Основные правила системы:
- заявитель может создавать заявки и работать со своими заявками;
- исполнитель может работать с назначенными ему заявками;
- оператор и администратор имеют расширенные права;
- заблокированный пользователь не может создавать заявки;
- исполнитель может завершить только назначенную ему заявку;
- заявитель не должен иметь доступ к чужим заявкам.

Правила валидации:
- тема заявки — от 1 до 200 символов;
- описание — от 1 до 5000 символов;
- category_id должен быть положительным целым числом;
- дополнительные неизвестные поля не допускаются.

Необходимо подготовить тесты для следующих сценариев:

1. Успешное создание заявки через сервис.
2. Запрет создания заявки заблокированным пользователем.
3. Успешное назначение исполнителя.
4. Успешное завершение назначенной заявки.
5. Успешное создание заявки через API.
6. Отклонение заявки с некорректными данными.
7. Отклонение недопустимого идентификатора категории.
8. Возврат 404 при обращении к несуществующей заявке.
9. Запрет заявителю просматривать чужую заявку.
10. Запрет исполнителю завершать заявку, назначенную другому исполнителю.

Требования к реализации:
- использовать pytest;
- использовать FastAPI TestClient для API-проверок;
- использовать отдельную временную SQLite-базу;
- не изменять производственную базу данных;
- проверять не только HTTP-коды, но и содержимое ответов;
- использовать реальные имена функций, методов и полей проекта;
- не придумывать отсутствующие endpoint'ы;
- не изменять исходный код приложения.

Предложи структуру тестовых файлов и код тестов.
Для каждого теста поясни, какое требование он проверяет.
```

### 5. Контекст, предоставленный модели

Для подготовки тестов были изучены и предоставлены сведения о следующих компонентах проекта:

- `src/services/request_service.py` — бизнес-логика операций с заявками;
- `src/controllers/request_controller.py` — API-методы и проверки прав;
- `src/repositories/request_repository.py` — операции с базой данных;
- `src/schemas/request_schema.py` — правила валидации;

Также модели были переданы сведения о подготовленной тестовой инфраструктуре и способе запуска приложения через TestClient.

### 6. Результат

В результате были подготовлены три группы тестов.

**Тесты бизнес-логики — `test_request_service.py`:**

**API-тесты — `test_request_api.py`:**

Для тестовой среды была подготовлена отдельная база SQLite. Она создаётся во временном каталоге для выполнения тестов, а исходная база приложения не используется.

## Взаимодействие № 2. Диагностика ошибки при регрессионной проверке

### 1. Дата и этап

09.11.2026. Проверка способности автоматизированного теста обнаруживать нарушение разграничения доступа.

### 2. Задача

Передать модели обезличенный фрагмент логики контроллера и результат неуспешного выполнения теста.

Требовалось определить:
- почему тест завершился ошибкой;
- какое условие системы нарушено;
- является ли ошибка проблемой самого теста или ожидаемой реакцией на изменение проверяемой логики;
- что следует проверить для подтверждения причины.

### 3. Модель

GPT-6.

### 4. Промпт

```text
Ты выступаешь в роли QA Automation Engineer.

Проверяется FastAPI-приложение с разграничением доступа
к заявкам по ролям пользователей.

Тест должен проверять следующее требование:
заявитель не может просматривать заявку другого пользователя.

Ожидаемое поведение:
HTTP 403.

Фрагмент проверяемой логики в изолированной экспериментальной копии:

if role == "Заявитель":
    pass

Выполнен автоматизированный тест:

def test_applicant_cannot_view_another_users_request(
    client, login, test_data
):
    login("user1", "User123!")
    request_id = test_data["requests"][
        'Нужен доступ к папке "Отчеты"'
    ]

    response = client.get(f"/api/requests/{request_id}")

    assert response.status_code == 403
    assert response.json()["detail"] == "Нет доступа к этой заявке"

Фактический результат запуска:

FAILED
assert 200 == 403

Один тест завершился ошибкой.

Проанализируй ситуацию:
1. Почему возникло расхождение между ожидаемым и фактическим результатом?
2. Какое правило доступа перестало выполняться?
3. Почему тест правильно обнаруживает проблему?
4. Какие действия нужно выполнить для подтверждения диагноза?
5. Нужно ли изменять сам тест или проверяемую логику?

Не предлагай менять рабочую версию приложения.
Эксперимент выполняется только в отдельной копии проекта.
```

### 5. Контекст, предоставленный модели

Для анализа использовались:
- проверка доступа к заявке в `request_controller.py`;
- тест `test_applicant_cannot_view_another_users_request`;
- тестовые данные, содержащие заявку другого заявителя;
- фактический результат выполнения pytest.

Эксперимент проводился в отдельной копии проекта. Рабочая версия репозитория не изменялась.

### 6. Результат

Причина ошибки — отсутствие проверки принадлежности заявки текущему заявителю.

В исходной логике контроллера предусмотрено сравнение идентификатора заявителя из заявки с идентификатором текущего пользователя.

В экспериментальной копии проверка была временно отключена. Из-за этого запрос к чужой заявке перестал отклоняться и API вернул HTTP 200 вместо ожидаемого HTTP 403.

Таким образом, тест завершился ошибкой не из-за неправильного ожидания, а потому, что экспериментальное изменение нарушило проверяемое требование безопасности.

**Фактический результат:**

```text
assert 200 == 403
1 failed
```

После эксперимента исходная проверка доступа была восстановлена в экспериментальной копии.

Рабочая версия проекта при этом не изменялась.

### 7. Самостоятельная оценка результата

Диагноз модели соответствует фактическому изменению кода и результату тестирования.

Тест действительно обнаруживает нарушение ограничения доступа: при отключении проверки принадлежности заявки заявитель получает доступ к чужой заявке, а автоматизированное утверждение фиксирует несоответствие HTTP-кода ожидаемому значению.

Изменять сам тест не потребовалось. Его ожидаемый результат — HTTP 403 — соответствует требованиям системы.

Эксперимент подтвердил, что тест не просто проходит на корректной версии приложения, но и способен обнаружить регрессию в проверке прав доступа.
